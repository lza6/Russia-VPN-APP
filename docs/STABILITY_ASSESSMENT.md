# 稳定性评估 — 这批节点能不能"长久稳定"

> 用实测数据回答"持久可用代理 IP"这个诉求。结论前置：
> **技术上具备长期可用的基础（10 年证书 + 无轮换），但节点存活是渐进的、上游不清理死节点，
> 必须自建定期测活轮换。延迟对中国大陆用户偏高（400-900 ms），带宽 2-4 Mbps 量级。**

## 1. "长期"这件事的三个层面

| 层面 | 实测结论 | 依据 |
|------|---------|------|
| **凭证寿命** | ✅ 长（10 年） | CA 证书 `notAfter` 到 2035-12，客户端证书同批签发；**无任何短期轮换机制**（无 token、无过期重签、无设备绑定） |
| **入口可达性** | ⚠️ 中 | 1167 条里 442 条已死（无任何 TLS 响应），占 37.9% |
| **出口可用性** | ✅ 高 | 握手存活节点中，15/15 抽样样本出口可用（100%），出口国家 15/15 匹配标称 |

换句话说：**只要节点活着，它就是长期稳定的**——问题在"节点会死，而目录不会告诉你哪个死了"。

## 2. 节点衰减的实证

按配置更新年份分组的存活率：

| 更新年份 | 存活 / 总数 | 存活率 |
|---------|------------|--------|
| 2024 | 235 / 289 | 81% |
| 2025 | 242 / 524 | **46%** |
| 2026 | 248 / 354 | 70% |

2025 年那批 524 条配置里过半已废弃，但**依然在 `allservers` 里正常下发**（`status` 恒为 0）。
这意味着：

- 上游不做目录清理，也**不提供任何可用性信号**
- 任何对接方都必须自己测活，且**必须定期重测**（不是一次性筛选）

## 3. 性能画像（15 节点隧道实测）

| 指标 | 分布 | 说明 |
|------|------|------|
| 握手耗时 | P50 2.50s / P90 3.34s / P95 5.15s | 含 TCP + TLS1.3 1-RTT + PUSH 往返 |
| 隧道 RTT | 426 — 1629 ms（中位 ~650 ms） | 中国大陆 → 北美/欧洲的物理距离成本 |
| 带宽 | 2.6 — 4.2 Mbps（抽样 2 个） | 1MB 单流实测，受 BDP / 慢启动限制，非上限 |
| 异常值 | 1 节点 RTT 3.6 s | 同 IP 段内也有明显快慢差异 |

带宽量级判断：**够跑 API 类业务（LLM 转发、网页抓取的小包请求），不够跑流媒体/大文件**。
延迟量级判断：**不适合对 RTT 敏感的交互场景**；作为并发代理池的一部分稀释个别慢节点可以接受。

## 4. 若要真用，必须自建的三个机制（本项目不提供）

1. **定期测活轮换**：`tools/probe.py` 已可复用，建议 6-12 小时全量跑一次（约 2.5 分钟），
   只把 `verdict == ALIVE` 的节点放进可用集。
2. **双阈值摘除**：连续 2 轮握手失败才摘除（单轮抖动很常见，一次失败的节点下一轮常常恢复）。
3. **协议转换层**：这些节点是 OpenVPN（`udp/1194` + 证书），不是 SOCKS5/HTTP 代理。
   要用必须起隧道再在隧道内做 SOCKS5 出口（通用做法：每节点独立 netns，隧道 + microsocks，
   宿主只用 netns 内的 SOCKS5 端口），成本高、并发上限受本机 netns/tun 数量限制。

## 5. 结论

| 用途 | 判断 |
|------|------|
| 研究 demo / 协议学习 | ✅ 完全够用，数据齐全 |
| 作为生产代理池的**主源** | ❌ 不推荐：37.9% 死节点、延迟高、无 SLA、凭证非授权 |
| 作为生产池的**低权重备用源** | ⚠️ 技术可行，但需自建上节三个机制 + 承担上游随时封端口的风险 |
| 需要"长久稳定 IP"的商业场景 | ❌ 应走正规付费代理/IDC 自建，这批节点没有服务承诺 |

**一句话**：稳定性瓶颈不在技术（证书 10 年、协议扎实），而在**上游不保证、节点会静默死亡、
且使用本身未获授权**。
